# G30 V01: report-boundary financial containment

This is containment for newly gathered reports, not a completed valuation model or a verified connector implementation. No current Stripe/Xero writer supplies an authenticated `RevenueProvenance` contract. The trusted producer registry is deliberately empty: even complete or spoofed metadata cannot admit valuation. Bare founder `mrrAud`/`arrAud`, legacy signals, snapshots and account evidence therefore cannot unlock numerical valuation. Previously stored reports are not rewritten.

The gather boundary now applies qualification before both connected financial evidence and valuation admission. Unqualified observations retain their provider, capture date and explicit rejection reasons. Their amounts, gross margin, operating expenses, churn and prior MRR are not copied to the report's financial result projection or citable evidence text. Raw source data remains in its original store for review; it is not relabelled as an established fact. Unqualified Stripe/Xero generic signal rows are likewise reduced to a notice, preventing a second numeric-evidence route. Tests pass the actual rows through `itemsFromEvidenceRows` to verify this boundary.

The future producer contract supports only complete native-AUD recurring-contract MRR, a source identifier/provider, matched owner/project/business/entity and matching source entity, capture/as-of dates, and an amount tied to that provenance. Explicit zero passes amount validation, remaining distinct from missing or invalid amounts; it still requires trusted attestation, so no zero-valued input bypasses the currently empty registry. Currency conversions, accounting-period revenue, inferred ARR, historical growth, and arbitrary legacy field names are not accepted. Different qualified amounts do not silently resolve via provider preference. Structural validation does not independently authenticate evidence. Before enabling any registry entry, a reviewed server-only producer must bind authenticated source retrieval to the current owner/project/business and source entity, not copy client/model metadata. Adding an identifier to the registry alone is not sufficient.

Producer work must precede re-enabling these valuation inputs:

- Stripe: reconcile explicit account/entity mapping, pagination/completeness, interval counts, recurring pricing basis and native currency; distinguish errors/partial pulls from proven zero. Any FX support needs separately reviewed units/rate/date/source, not a static fallback.
- Xero: request and preserve exact accounting dates, report currency and organisation mapping; comparison periods do not constitute a summed three-month window. Accounting revenue must not be labelled MRR. A separate eligible valuation method is required.
- Founder figures: retain exact input quote/document, metric, currency, period/as-of and assessed business; distinguish stated figures from externally established figures. Do not accept the existing parser's bare annual/monthly guesses as source provenance.

Broader limitations remain: original report context, Evidence Hub uploads/reviewer documents and legacy independent valuation/certificate consumers have separate paths outside this narrow connector admission change. General financial claim entailment and uploaded evidence qualification remain required. The CFO builder's output is still not proof of V02 method suitability or V03 reconciled investment value. This phase does not add DB schema, repair connectors, alter existing scores, retroactively modify reports, or certify readiness for sale.

Validation: focused qualification adversarial fixtures and gather integration tests; no external API calls, inference, migrations or production reads/writes. Synthetic fixtures exercise structurally complete but spoofed provenance, which remains rejected, and the valid-zero/invalid-amount distinction. They are not evidence that a production producer exists.
