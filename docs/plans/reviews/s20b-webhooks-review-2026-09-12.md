# S20-B signed outbound webhooks — security review (2026-09-12)

Scope: `web/src/lib/webhooks/{sign,registry,store,dispatch,http}.ts`, `api/webhooks/**`, `api/cron/webhook-dispatch`, 6 emitter sites, `webhooks-section.tsx`, migration `0336_webhooks.sql`, `docs/page.tsx` snippet. Read code + all 8 test files (67 tests, all green). `WEBHOOK_SECRET_KEY` confirmed set in `web/.env:206`; crontab has `*/5 webhook-dispatch --timeout 120`.

## Findings

**P1 — Revoked project member keeps a live event channel + management rights.**
`src/lib/webhooks/http.ts:275` returns the endpoint to its creator *before* any project check (`if (endpoint.user_id === user.id) return ...`). For a project-level endpoint this means the creator (an admin at creation time) can still PATCH/DELETE/test and read deliveries after being removed from the project. Worse, `registry.ts:268` / `store.ts:120-130` select project endpoints by `project_id` + `active` only, and the dispatcher's only gate is the *creator's plan* (`dispatch.ts:268,292`), so `svi.rescored` and `evidence.uploaded` (with filename, sha256, score deltas) keep flowing to the ex-member's URL indefinitely. Nothing deletes/deactivates `webhook_endpoints` on member removal (grep: no consumer outside `lib/webhooks`). Scenario: agency admin adds a project endpoint pointing at their own server, founder later revokes them — data keeps arriving. The owner *can* see and delete it via `GET ?project_id=` but must know to. Fix (minimal): in `loadEndpointForCaller` require `assertProjectAccess(user.id, endpoint.project_id, "admin")` for every project-level endpoint regardless of creator; and in `dispatchDue`, for endpoints with `project_id`, drop/`dead:creator_not_member` those whose `user_id` is no longer owner/admin+ (one `project_role_for` batch per tick). Optionally cascade-deactivate on member removal.

**P2 — Owner SELECT policy exposes `secret_hash` / `secret_enc` via PostgREST.** `0336_webhooks.sql:124-125` grants `authenticated` owners SELECT on all columns; Supabase default table grants apply and the browser client + `AuthSyncClient` exist (`src/lib/supabase/browser.ts`, `layout.tsx:202`). With the key set the blob is AES-GCM (not recoverable), but the design claim "secret never leaves the server" (`http.ts:200`) only holds for the API path. The app never reads these tables through RLS. Fix: `REVOKE SELECT (secret_hash, secret_enc) ON public.webhook_endpoints FROM anon, authenticated;` (or drop both owner_select policies). Anon: `auth.uid()` NULL → zero rows — checked OK.

**P2 — `failure_count` lost-update race (author-noted) — assessed: availability only, but real.** `dispatch.ts:224-241` computes `endpoint.failure_count + 1` from the row loaded at tick start (`:267`) and writes it back. Overlap is plausible: 50 deliveries x 8 s timeout = 400 s > the 300 s cron period (`maxDuration=120` is Vercel-only; the standalone handler keeps running after curl's `--timeout 120`). Two overlapping ticks undercount → auto-disable delayed; also a user PATCH `active:true` (`[id]/route.ts:216`) racing a tick holding count 19 gets written back to 20 and re-disabled immediately. No double-send (lease is per-delivery, taken right before send, 120 s > 8 s). Fix: atomic `UPDATE ... SET failure_count = failure_count + 1 RETURNING failure_count, active` (RPC) and disable on the returned value; or lower batch to ~15 per tick.

**P2 — DNS-rebinding TOCTOU (noted).** `checkOutboundUrl` (`outbound-url.ts:180`) resolves with `dns.lookup(all)`, then `fetch` (`dispatch.ts:125`) resolves again — a short-TTL name can flip to a private IP between the two. Every address must be public, `redirect:"manual"`, and the check runs on every attempt, which limits exposure but not the race. Fix: pass an undici `Agent({ connect: { lookup } })` whose lookup re-validates via `isPrivateIp` (or pins to the checked `addresses`).

**P2 — Prod fail-open if the sealing key is ever missing.** `sign.ts:123-124` silently stores `obf:` base64 when neither env var is set; `openSecret` (`:135`) also accepts `obf:` regardless of key presence. Today the key is set, but a mis-deployed env would persist plaintext-equivalent secrets. Fix: in `sealSecret`, throw when `NODE_ENV==="production"` and no key; the create route already returns 500 on insert failure.

**P2 — Docs verifier can throw instead of returning false.** `src/app/docs/page.tsx:361-362` compares string lengths then `timingSafeEqual(Buffer.from(got,"hex"), …)`; a non-hex `v1` of length 64 decodes to fewer bytes → `RangeError` (receiver 500s). Fix: validate `/^[0-9a-f]{64}$/i` first (as `sign.ts:77` does) or compare buffer lengths.

**P2 (low) — PATCH has no rate limit** (`[id]/route.ts:180`); create is 20/h, test 10/min. A URL change triggers DNS resolution each call; cheap DoS/DNS-oracle surface. Fix: `enforceRateLimit("webhooks-patch", user.id, request, 30, 60_000)`.

## Checked OK
1. Secrets: returned once (`api/webhooks/route.ts:142`, test "returns the secret ONCE"); `publicEndpoint` strips hash/enc (`http.ts:201`); no route or store ever returns `secret_enc`; deliveries API returns ids/status only (`http.ts:219`); envelope never carries the secret; `apiRoute` audit never reads body/response (`audit/api-route.ts:32`), `detail.note` is null here; `console.error` in enqueue/dispatch logs ids only. With the key set `sealSecret` never emits `obf:` (`sign.ts:123`). Rotation = delete + recreate (no secret-reveal path).
2. SSRF: `validateEndpointUrl` at create (`route.ts:121`), PATCH (`[id]/route.ts:198`), test ping and every attempt via `sendOnce` (`dispatch.ts:107`, `sendPing:347`); http:// refused (`isHttpsUrl`) + DB check `url ~ '^https://'`; `[::1]`, `::ffff:127.0.0.1`, `0.0.0.0/8`, `localhost`, `*.internal`, numeric-disguised v4, single-label names all refused; 3xx → `redirect_not_followed` failure (`:139`, tested); credentials-in-URL refused; response body cancelled, never stored.
3. Signature: HMAC-SHA256 over `${t}.${body}` where `body` is the exact `JSON.stringify` string passed to fetch (`dispatch.ts:113-131`); `t` unix seconds; `verifySignature` uses `timingSafeEqual` with length guard + ±300 s tolerance; header format and the docs snippet's `t=…,v1=…` / `${t}.${rawBody}` match; delivery id stable across retries (idempotency).
4. AuthZ: user-level endpoints creator-only (404 otherwise); `GET/POST ?project_id` → `assertProjectScope(admin)`; editor 403 / non-member 404 tested; plan gate on create (402) and re-checked per tick (`usersAllowedWebhooks` → `dead:plan_lapsed`, no failure counted); 10/scope enforced (409). Caveat: P1 above.
5. Payloads: ids + numbers + filename/sha256 only; `funding.report_ready` uses `reportUrl(id)` **without** token and skips guest rows (`reports.ts:193-202`); `evaluation.report_ready` → `userIds:[evaluator]`, `projectEndpoints:false` in both the route (`report/route.ts:301`) and batch runner (`:202`) — founder's endpoints never receive it; no emails, no share tokens.
6. Dispatcher: `claim` is one conditional UPDATE (`status in (queued,failed) AND lease free`) — proven PostgREST `.or()` idiom; ladder 1m/10m/1h/6h → `dead` at 5; `dead` terminal (never re-listed); auto-disable at 20 with one deduped notification (24 h throttle); 8 s AbortController; batch clamped ≤ 50 (route + lib); `dry` returns before claim, writes nothing (tested); cron bearer-auth required, 401 when `CRON_SECRET` unset.
7. Emitters: all six `await enqueueWebhook(...)`, which is fully try/catch-wrapped and returns `{queued:0}` on any error (tested with a throwing store); cost is ≤ 2 indexed reads + 1 insert, run after the primary write commits. Not fire-and-forget, but bounded and non-throwing.
8. RLS enabled on both tables; service-role policy for writes; anon reads nothing. (Column exposure to owners: P2 above.)
9. UI: secret only in `revealed` state, rendered once with a Copy button; cleared on "I have saved it" and on delete (`webhooks-section.tsx:162,282`); no localStorage/sessionStorage; no re-fetch path exists.

Verdict: ship-blocking = P1 (revoked-member channel). Remaining items are P2 hardening.
