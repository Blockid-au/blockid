# S17-A security review — shared projects / member-aware access
Range: afc4d55a5 (feat) + a83c67cd8 (merge) + 8a7a657bb (renumber → 0331). Read-only; code + tests verified.
Question: can a non-member read/write another user's project data, or can a viewer mutate?
Answer: **non-members: no** (all paths key on `user_id` + `status='accepted'`). **Viewers: YES, via routes S17-A did not touch** (P1 below). Plus one cross-project leak for members inside the owner's account.

## P1-1 — Viewer (and any member) can mutate/read the owner's startup record through ~20 routes that were NOT made role-aware
- `web/src/lib/projects.ts:466-520` `getActiveProject` now falls through to accepted memberships, so `getProjectIdFromRequest()` (`:562`) returns a SHARED project id for any member, viewer included.
- `web/src/lib/projects.ts:664-676` `findOrCreateSVIAccount(callerEmail, projectId)` and `:788-798` `findSVIAccountWithFallback` now resolve to the OWNER's `svi_accounts` row when the caller is not the owner. Pre-S17-A a member got a split row under their own email (harmless); now they get the owner's.
- Neither helper checks membership/role — they trust `projectId`. Every route that still does `getProjectIdFromRequest()` + `findOrCreateSVIAccount(user.email, projectId)` therefore writes to the owner's account with **no role gate**:
  - `app/api/evidence/disconnect/route.ts:57-83` DELETE — deletes owner's `svi_evidence` + `oauth_connections`
  - `app/api/metrics/route.ts:133-151` POST — upserts `startup_metrics` under owner's account
  - `app/api/evaluation/route.ts:207-208`, `app/api/evaluation/[criterionKey]/ai-score/route.ts:69,190`, `app/api/evidence/connect-url/route.ts:164-165`, `app/api/evidence/bank-statement/route.ts:185-186`, `app/api/integrations/github/manual/route.ts:56-57`, `app/api/svi/route.ts:485-526`, `app/api/blockchain/create-token/route.ts:66-67` (POST), `app/api/oauth/*/callback` (link an integration to the owner's account)
  - Reads with no viewer/membership re-check: `app/api/score/route.ts:1029-1030`, `app/api/svi/docx/route.ts:116-118`, `app/api/svi/report-section/route.ts:145-161`, `app/api/svi/dimension-analyze/route.ts:103-110`, `app/api/valuation/{route,vc,clevel}.ts`, `app/api/blockchain/token/route.ts:27`
- Scenario: viewer V accepts invite to owner O's project P (cookie `blockid_project=<P uuid>` is set by `members/accept`). V calls `DELETE /api/evidence/disconnect {evidence_type:"stripe"}` → `getProjectIdFromRequest()`=P → `findOrCreateSVIAccount(V.email,P)` → owner-email fallback → O's account id → O's Stripe evidence + connection deleted. Same for `POST /api/metrics`.
- Minimal fix (choose one): (a) make `findOrCreateSVIAccount` / `find*WithFallback` take the resolved `dataEmail` only and drop the internal `resolveProjectDataEmail` fallback, so unconverted routes keep the old split-row behaviour until they are migrated to `getProjectScope("editor")`; or (b) have `getProjectIdFromRequest()` stay owner-only and add `getProjectScope()` to every route above. (a) is one file and restores the pre-S17-A blast radius immediately.

## P1-2 — `api/evidence/analyze`: member on project A can analyze/mutate evidence from the owner's OTHER projects
- `web/src/app/api/evidence/analyze/route.ts:198-205`: `ownsEvidence = (account.project_id === projectId) || accountEmail === dataEmail`. For a member, `dataEmail` = owner's email, so ANY `svi_accounts` row of the owner (project B, legacy null-project) passes the email clause.
- Scenario: editor E on O's project A posts `{evidenceId: <id from O's private project B>}` → passes → reads B's evidence label/value into the AI prompt, inserts `evidence_analyses`, updates B's `svi_evidence.svi_impact/dimension` (`:288-296`), spends E's credits. Cross-project write with 200.
- Fix: when `scope && !scope.isOwner`, require `account.project_id === scope.projectId` only (email clause is owner-only legacy path). Add a test — `evidence/analyze` has **no test file**.

## P2
- **P2-1 legacy-null fallback leaks owner's pre-project record to members**: `projects.ts:800-808` / `:866-886` — after the owner-email retry fails, `findSVIAccountWithFallback` / `findLatestAnalysisWithFallback` fall to `(ownerEmail, project_id IS NULL)`; the latter also **UPDATEs** owner's orphaned `svi_analyses.project_id` (`:876-881`) — a write to owner data triggered by a member (viewer via P1-1 routes). Fix: skip the legacy fallback when `dataEmail !== callerEmail`.
- **P2-2 data-room/generate cross-project**: `app/api/data-room/generate/route.ts:85-89` `svi_accounts .eq("email", dataEmail).maybeSingle()` has no `project_id` filter; `:204` shareholders by `ownerUserId`. Member of A compiles a room from whichever of O's records match (owner-level, not project-level). Same shape in `data-room/readiness/route.ts:110-116,159-167` (owner's latest `data_rooms`, P0 doc names returned). Fix: filter `svi_accounts` by `project_id`; scope `data_rooms` by `(user_id, project_id)` (the upsert at `generate:306-316` already keys on it).
- **P2-3 existence oracle in `/api/projects/[id]/members`**: `lib/project-members/scope.ts:189-215` → missing project 404, existing-but-not-member 403. `assertProjectAccess` correctly returns 404 for both; the members route uses the older helper. Fix: map `forbidden`-with-no-membership to 404, or route through `assertProjectAccess`.
- **P2-4 `project_role_for()` callable by any `authenticated` JWT for arbitrary (project,user) pairs**: `web/supabase/migrations/0331_project_member_access.sql:52-80` — SECURITY DEFINER, `search_path=public` pinned (good), REVOKE from public (good), but `GRANT … TO authenticated` lets any Supabase-auth user probe roles by UUID. anon cannot call it. Fix: `AND p_user_id = auth.uid()` inside the body, or grant to `service_role` only. (App uses service-role for all reads, so today it is inert.)
- **P2-5 invite token is bearer-only**: `lib/project-members/scope.ts:345-390` `acceptInvite` binds `user_id` to whoever presents the token; `user_email` is never compared to the accepting user. Pre-existing, but S17-A now makes that membership grant real data access. Fix: require `existing.user_email === user.email` (or explicit owner-approved mismatch).
