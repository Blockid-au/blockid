## P1-1 — id-keyed mutations check the owner's `account_id`/`user_id` only, not `project_id`: editor on project A mutates owner's project B rows
- `app/api/cap-table/route.ts:272` (issue_shares), `:355` (update_shareholder), `:442` (DELETE) — `.eq("id", shareholderId).eq("account_id", accountId)`; no `.eq("project_id", scope.projectId)`. GET (`:40-41`) is project-filtered, so the id must come from elsewhere (UUID, so oracle-only — but the boundary is wrong: same class as S17-A P1-2).
- `app/api/esop/grants/[id]/route.ts:24-25,72-73` and `app/api/esop/div83a-check/route.ts:45` → `lib/esop-grants.ts:163-171` `getGrant(id, userId)` / `:181-194` `updateGrantStatus` — `(id, user_id)` only; `esop_option_grants.project_id` (0089) is never applied on the single-row paths (`listGrants` `:118-122` does apply it).
- `app/api/data-room/auto-fill/route.ts:94,284` — `data_room_documents` by `(id, account_id = ownerUserId)`; the document's room (`data_room_id` → `data_rooms(user_id, project_id)`, 0062/0123) is not checked, so an editor on A rewrites `template_content` of a document in the owner's project-B room and spends their own 0.25 credits.
- Scenario: O owns A and B; E is editor on A with any B row id → 200, B mutated. Pre-S18 these paths were owner-only (`user.id`), so the blast radius is new.
- Fix (all three): when `scope` is non-null add `.eq("project_id", scope.projectId)` (cap-table pre-checks; `getGrant`/`updateGrantStatus` gain a `projectId` arg); auto-fill: join through `data_rooms` (`.eq("data_room_id", room.id)` after resolving the project's room as `readiness` does at `:122-127`). Add a "foreign project row → 404" case to `cap-table/route.test.ts` and `esop-grants.test.ts` (none today).

## P1-2 — `auth/analytics/callback` writes evidence + an OAuth token under any state-supplied email, unauthenticated (pre-existing; S18-A touched it and deferred it)
- `app/api/auth/analytics/callback/route.ts:24-31` gates `admin` via `projectScopeOrRedirect`, but an unauthenticated caller yields `scope = null` (not a denial) → `:57-61` `email = state.email` (no CSRF, no session, never compared to a user) → `:96` `findOrCreateSVIAccount(scope?.dataEmail ?? email, null)` → upsert `oauth_connections` + insert `svi_evidence` (svi_impact 8–15) on the victim's legacy null-project account. The comment says "see report" — no report documents it (grep of docs/plans: 0 hits).
- The five `oauth/*/callback` routes have CSRF binding but the same fallback `scope?.dataEmail ?? email` (ga4 `:123`, github `:139`, linkedin `:91`, stripe `:69`, xero `:149`); `state.email` is never compared to the session user → a signed-in user with no project can link/insert evidence under another email's legacy record.
- Fix: in every callback require `getCurrentUser()` and `state.email === user.email` (redirect `*_email_mismatch` otherwise); fallback must be `?? user.email`, never the state value. Delete or session-gate `auth/analytics/callback` if it is a dead legacy redirect URI.
