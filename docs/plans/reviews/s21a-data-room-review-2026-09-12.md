## P1

**P1-1 NDA acceptance email overwrites the founder's `investor_email` → identity spoof in showcase reviews.**
`api/data-room/nda/route.ts:123` `...(parsed.email ? { investor_email: parsed.email } : {})` writes the investor-typed email onto `data_room_access_tokens`. `api/showcase-reviews/route.ts:7,63,92` copies `accessToken.investor_email` as `reviewer_email` explicitly "so the reviewer can't spoof an identity", and upserts on `(project_id, reviewer_email)`. Scenario: token holder accepts the NDA with `email: "partner@blackbird.vc"`, then POSTs a review — it lands under that email, and it also overwrites the founder's own record of who the link went to (and `watermark` fallback at pdf/route.ts:119). Test at nda/route.test.ts:148 pins the overwrite as intended. Fix: keep `viewer_email` on the ledger only; never write `investor_email` from the acceptance body (or write only when the column is null AND showcase-reviews stops trusting it). Also fold the email into the watermark label only via the ledger row.

**P1-2 No rate limit on the three anonymous token routes (NDA POST, engage POST, PDF GET).**
`proxy.ts:57-73` BUCKET_ROUTES has no `/api/data-room/*` entry; nginx `blockid-live` has no `limit_req`; `apiRoute()` only audits. So `api/data-room/nda` POST (spec asked for a limit), `engage` POST and `share/[token]/pdf` GET (server-side @react-pdf render, `maxDuration = 60`) are unlimited per IP. Scenario: one token holder (or anyone, for nda/engage which 404/403 on bad tokens) loops the PDF route → CPU exhaustion on the single production box; engage POST with a rotating `section` string bypasses the 30 s dedupe (keyed on section, engagement.ts:92-104) and inserts unbounded rows. Fix: add `["/api/data-room/nda","investor-link"]`, `["/api/data-room/engage","investor-link"]`, `["/api/data-room/share/","investor-link"]` (or a new small bucket) to BUCKET_ROUTES; keyed by IP for anon traffic already (clientIdentity).

## P2

**P2-1 Attacker-named sections pollute the founder's heatmap columns.** engage/route.ts:183 builds the heatmap without `sectionOrder`; `parseEngageEvent` accepts any ≤120-char `section`. A token holder can inject arbitrary column headers (rendered by React, no XSS) into `engagement-heatmap.tsx`. Fix: pass the room's real folder list as `sectionOrder` and drop unknown sections in `buildEngagementHeatmap`, or validate `section` against `data_room_documents.folder` + the two fixed page sections in POST.

**P2-2 Section dwell is never tracked in the session that accepts the NDA.** `engagement-tracker.tsx:45-106` queries `[data-engage-section]` once on mount with deps `[token]`; `nda-gate.tsx:64` calls `router.refresh()`, which re-renders the sections but does not re-run the effect, so the IntersectionObserver observes nothing until a hard reload. Fix: key the tracker on `room.nda.status` (`<EngagementTracker token=… key={room.nda.status}>`) or use a `MutationObserver`.

**P2-3 Watermark silently absent on anonymous links while the page says "watermarked for you".** `watermarkLabel()` returns null when the link has no name/firm/email (watermark.tsx:56-60, pdf/route.ts:115-121), yet `load.ts:212` sets `watermarked = entitled && watermark_enabled` regardless, and page.tsx:249 renders the badge. Fix: fall back to a short link id (`link ${id.slice(0,8)}`) so every served PDF traces to a disclosure, or compute `watermarked` from the same recipient rule.

**P2-4 Engage POST token-state oracle + partial state check.** engage/route.ts:58-64 answers 403 "Invalid or expired token" vs "Link has expired" — an expired token is distinguishable from a nonexistent one; it also ignores `revoked_at` (fine today because both revoke paths set `is_active=false`, but `shareLinkState` is the shared rule). Pre-existing, but S21-A touched the block. Fix: use `shareLinkState()` and one 403/404 body.

**P2-5 Plan lapse fails open.** `ndaGate(..., entitled=false)` → `not_required` (nda.ts:97), so a room with `nda_required=true` whose owner drops to Free serves documents without the gate to every existing link, and PDFs without watermark. Documented as intended ("Free rooms unaffected"), but for an NDA the safer default on lapse is to withhold documents (or keep the gate for links that already accepted). Product decision — flagging, not asserting.

**P2-6 Ledger `account_id` uses the minter, not the owner.** nda/route.ts:102 `account_id: link.account_id ?? room.user_id`; links minted by a member via `api/data-room/access` carry the member's id, so RLS policy `drna_owner_select` (0339:104) would let that member, not the owner, read via the authenticated role. No live impact (settings GET uses service role scoped by `data_room_id`), but the RLS comment "room owner (tenancy key)" is wrong. Fix: `account_id: room.user_id ?? link.account_id`.
