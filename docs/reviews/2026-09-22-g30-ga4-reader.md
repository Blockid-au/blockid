# GA4 site-scoped reader and verified account limits

22 September2026. Source fixes0ab8b5b43 and653a94677; website release pending this evidence record.

The production environment supplies an existing service-account email/key pair. The Admin helper accepted that pair; the daily traffic reader required a separate JSON credential and therefore reported unconfigured. The reader now reuses the shared credential/property normalization, preserving existing JSON support and readonly scope. No key is copied into source, no property is created and no analytics account is modified.

A readonly Data API request against the configured property succeeded. Its seven-day hostname results contained SVI activity, not observed BlockID activity. Both public documents contain the same GA measurement ID; the property aliases agree. Therefore accepting credentials alone would let the BlockID daily dashboard label sibling-site traffic as its own.

Every daily totals, pages, events, acquisition and trend request now includes an exact hostname list for blockid.au/www.blockid.au, case-insensitive. New snapshots record hostname_scope. Unknown hosts, staging and startupvalueindex.com are not silently included. Generic runReport remains a passthrough for explicitly scoped callers. Existing historical snapshots are not rewritten.

A real readonly Data API query accepted this hostname filter and returned no observed BlockID events in the checked seven-day window. This verifies API/filter operation, not that BlockID event collection is functioning or that traffic never occurred.45 focused reader tests pass, including credential-pair authentication and all five filtered queries; requests in tests are mocked, not sent to Google.

Admin API inspection remains blocked by api_disabled. Cloudflare gateway inspection returned403/code10000 with the configured token. Property/web-stream settings, Search Console linkage and collection delivery/deduplication remain unverified. GA4 is measurement infrastructure, not a mechanism to push rankings.
