# CFO V04-P1 — Stripe producer qualification disposition

24 September 2026. Source audit only, followed by existing offline tests. No OAuth exchanges, account queries, connector writes, migrations or inference. This is **not** a positive producer acceptance receipt.

## Decision

Keep the report-boundary trusted producer registry empty. The existing authenticated Stripe connector is a useful starting point, but its output does not establish complete native-AUD recurring revenue for the assessed business. Adding a producer name, copying snapshot JSON into `RevenueProvenance`, or equating an OAuth grant with legal-entity verification would bypass unresolved facts.

The new CFO scenario core remains usable with explicitly attributed assumptions. It must not upgrade these connector aggregates to accepted financial evidence. V04-P1 is **open**, independently of deterministic scenario arithmetic and UI delivery.

## Minimum implementation sequence for a real positive path

1. **Bind the OAuth grant before retrieval.** Pin project and initiating principal into server-controlled OAuth state; re-check current permissions on callback. Persist source account ID, live/test mode, connection revision and reviewed source-account-to-business mapping. Reading a Stripe business display name alone is insufficient to claim this mapping. Fail closed if the project is absent, ownership cannot be resolved, mapping is revoked or source identity differs.
2. **Create a strict native-AUD producer.** Retrieve account identity and traverse all subscription pages and all subscription-item pages with bounded budgets, duplicate/cursor-loop detection and explicit abort on partial pulls. The producer returns incomplete/unsupported, never a fabricated complete amount, when limits or upstream errors occur.
3. **Support a narrow price subset first.** Native AUD, explicit quantity and amount, fixed licensed recurring prices with explicit month/year interval and interval count. Define treatment of discounts, taxes, trials, paused subscriptions, pending changes, schedules and cancellation timing; reject unsupported tiered/metered/transform/currency configurations rather than estimating. Do not infer a missing unit amount as zero. A zero-priced explicit supported item can contribute zero.
4. **Persist producer-owned proof.** Store immutable source identifiers/digest, account identity, scope binding, completed pagination evidence, observation window, method version, qualified amount and exclusion policy in a service-only authority store. If provenance is carried through general JSON, authenticate it with a server-controlled attestation bound to all these fields; never trust an arbitrary producer string. Pin source as-of and captured times.
5. **Wire the full read path.** Read the qualified authority record by owner/project/entity/revision, verify attestation or trusted-store identity, then expose it to report gathering. Only then activate the exact versioned producer. Keep legacy Stripe/Xero signals out of this route. Do not let a newer unqualified legacy snapshot silently replace an admitted source.
6. **Acceptance before activation.** Positive fully paginated native-AUD fixture; authenticated empty active-subscription list yields explicit qualified zero; real zero price remains zero; no token, malformed body, 401/429/500, partial page, duplicate cursor, unsupported price, mixed currency, test mode, entity/project mismatch, revoked binding, wrong account and tampered amount all reject. Test actual producer → authority write/read-back → loader → `qualifyRevenue` → gather integration, not only an object constructed to resemble proof. Run a separately authorized controlled connector canary before marking production acceptance.

## Missing versus zero

`qualifyRevenue` already allows numerical zero through its amount check; it still requires authentic provenance. That distinction must remain. Current link-time fallback zero is **missing/error**, not proof of no recurring revenue. An authenticated, fully paginated successful empty set can establish zero only after source identity, scope and supported-contract policy are satisfied. Xero accounting revenue and founder management assumptions require separate metric contracts, not this MRR producer.

## Scope of completion

This audit resolves the implementation decision and documents the exact blocker; it does **not** complete V04-P1 or unlock valuation in newly gathered reports. No registry entry or connector behavior was changed. Existing tests exercise containment and legacy behavior, not complete Stripe data or an operational trusted producer.
